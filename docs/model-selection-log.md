## Final optimization: deductions, prompts and communication

Observed deductions included overnight-flight sightseeing before arrival; poor flight timing; long afternoon gaps; taxi-heavy routes; assumed daily spend; missing venue hours, coordinates and ratings; repeated supermarket branches; insufficient temple/cuisine/romantic coverage; and unsupported narrative claims.

Changes address those causes:

1. **System instructions:** exact candidate IDs; actual local arrival/departure dates and airport/rest buffers; whole-trip uniqueness; requested interest coverage; geographic grouping; realistic pacing; evidence-bound quality claims. Reviewer instructions distinguish material itinerary problems from text-only defects.
2. **User evidence:** place compaction now includes real ratings and coordinates, leaving missing facts null. The capped place pool preserves pinned venues then round-robins requested categories rather than dropping whole categories. Reversible F/H/P/T aliases shorten IDs, restored before unchanged deterministic checks; unknown IDs still fail.
3. **Flight sequencing:** `_flight_day_window` uses actual local dates. No stops precede arrival or exceed departure; buffers remain deterministic.
4. **Three-role communication:** one planner proposal; deterministic checks; at most one semantic correction assigned to the executor using verification and reviewer feedback; verification/review again; narrative executor receives reviewer feedback. Defects that alter itinerary facts still require a corrected plan and verification, never a prose-only assertion.
5. **Separate narrative routing:** opt-in `TARGETED_NARRATIVE_REVIEW=true` permits one text-only revision. Ambiguous/factual defects remain unresolved. The revision is labeled `revised_not_rejudged`, never assigned a fabricated improved score. This feature remains disabled pending semantic factuality validation.
6. **Transport discipline:** no provider retries; bounded requests and durable authorization before generation. Adaptive-v7 adds native JSON mode for non-thinking Qwen Flash, bounded reasoning for long single-city quality proposals, and adapter-level Kimi spacing covering both reviewer and evaluator.

Some deductions cannot be solved honestly by prompt wording: missing hotel stars and opening hours require provider evidence; flat meal/admission estimates need itemized data; cheapest-transit preferences need actual transit candidates and cost/timing support. The current deterministic inter-stop routing can select taxis while omitting those fares from the transfer total. Improving those data/tool contracts is a remaining product task, not permission to invent supporting facts or change the rubric.

These exploratory versions are not repeated controlled trials. Prompt, evidence and sequencing changes co-vary. Best results from different versions must not be pooled into a fictitious uniform protocol. Reused UUIDs count once.

### Historical source: README.md

# Agentic Travel Planner (Group 10)

A chat-based travel planner on AWS. You describe a trip ("Copenhagen 3 nights, Lofoten 4, Abisko 4, two people,
SGD 14,000") and an agent searches real flights, hotels, places and transfers, drafts an itinerary, checks it
with code (budget, dates, opening hours, travel times), improves it up to 3 times, and returns a day-by-day plan
with a PDF. You can keep chatting to change it.

**Design rule:** prices never come from the model. Every flight, hotel, transfer and place is looked up by ID in the
candidate pool that the search tools saved, and the verifier and PDF re-read prices from there.

## Architecture

```
Browser (web/index.html on CloudFront + S3, Cognito sign-in)
   │ chat (streamed)                      │ trips, PDFs, feedback
   ▼                                      ▼
AgentCore Runtime: agent/            API Gateway + Lambda tp-api-trips
   │  Intake → Gather → Propose → Sequence → Verify → Judge → Repair (≤3) → Deliver
   │  models: Claude Sonnet 4.6 (planner, adaptive thinking) · Haiku 4.5 (intake, chat, writing) ·
   │          Amazon Nova 2 Lite (judge) · automatic fallback to older models · prompt caching
   │  AgentCore Memory: remembers traveller preferences across trips
   ▼ MCP
AgentCore Gateway → 8 Lambda tools: lambdas/
   search_flights · search_stays · find_places · search_transfers · route_matrix
   sequence_day · verify_itinerary · render_pdf
   ▼
DynamoDB (cache + candidate pool, trips, itineraries, feedback) · S3 (PDFs) · Secrets Manager (API keys)
```

## What it can do

- Single- and multi-city trips (several hotels, flights or trains between cities, open-jaw flights)
- Real flight prices from Google Flights (SerpApi), with Duffel and sample data as fallbacks
- Personal preferences: diet, accessibility, hidden gems vs classics, family, indoor, free, hotel style/stars/area,
  direct flights and time windows, scenic trains
- Specific places by name (pinned), a named or already-booked hotel, day trips (e.g. Nikko from Tokyo)
- Mid-chat changes: "go to Osaka instead", "add dinner at Ichiran", "cheaper hotel", or a separate new trip that keeps
  dates/budget/travellers
- PDF plan with links, trip history, and a feedback panel (stars + five user-study ratings) on every plan
- Prompts can be managed in Bedrock Prompt Management (docs/prompt-management/ (development repository))
