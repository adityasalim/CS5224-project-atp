# Travel planner — Lambda functions

Eleven functions, one folder each: **nine agent tools** that AgentCore Gateway exposes over MCP, and **two API
back-ends** behind API Gateway. Every folder has a `lambda_function.py` handler (`lambda_function.lambda_handler`;
Python 3.13, x86_64). Deploy them with `scripts/create_lambdas.sh` (or upload the zips from `scripts/build_zips.sh`);
after that, CodeBuild redeploys any function whose folder changes on `main`.

| Folder | Gateway tool | What it does |
| --- | --- | --- |
| `tp-search-flights` | `search_flights` | Real fares from Google Flights via SerpApi, Duffel as fallback |
| `tp-search-stays` | `search_stays` | Hotels from liteAPI and Duffel Stays (order set by `STAYS_PROVIDERS`), mock as last resort |
| `tp-find-places` | `find_places` | Attractions, restaurants and cafes from OpenStreetMap, Amazon Location and Google Places |
| `tp-search-transfers` | `search_transfers` | Flights or estimated ground options between cities on multi-city trips |
| `tp-route-matrix` | `route_matrix` | Travel times between stops (Amazon Location, distance estimate as fallback) |
| `tp-sequence-day` | `sequence_day` | Pure code: orders a day's places around opening hours and travel times |
| `tp-verify-itinerary` | `verify_itinerary` | Pure code: checks every hard constraint, re-reading prices by ID |
| `tp-render-pdf` | `render_pdf` | Builds the itinerary PDF (uses the `tp-fonts` layer for non-Latin names) |
| `tp-ahmed-search-packages` | `search_agency_packages` | Published agency and guide packages that match the trip |
| `tp-api-trips` | (API Gateway) | Trip history, PDF links, feedback, stated preferences, chat history and background-run status |
| `tp-ahmed-agency-api` | (API Gateway) | Partner portal: agency registration, package management and admin approval (`marketplace_domain.py` holds the rules) |

Every function takes the signed-in user from the Cognito token, never from the request body.

## How they fit together

```
search_flights   ─┐
search_stays     ─┤
find_places      ─┼─► candidate pool in DynamoDB (pool:<id>, 24 h TTL) ◄─┬─ sequence_day
search_transfers ─┘                                                       ├─ verify_itinerary
route_matrix ◄─── sequence_day (optional, via Lambda invoke)            └─ render_pdf
```

The four search tools save every result as `pool:<id>` in `tp-dev-api-cache`. The other tools
look things up **by ID** there, so prices, names and links in the plan always come from the
providers, never from the model. That is the report's "prices are never generated by a model" rule.

Values: `CACHE_TABLE=tp-dev-api-cache`, `MOCK_MODE=true` to start, `SECRET_ARN` = your
Secrets Manager ARN, `PLANS_BUCKET` = your `tp-dev-plans-<suffix>` bucket.

API back-ends: `tp-api-trips` uses `TRIPS_TABLE`, `ITINERARIES_TABLE`, `FEEDBACK_TABLE`, `USERS_TABLE`,
`PLANS_BUCKET`, `MEMORY_ID` and `ALLOWED_ORIGINS` (see the docstring at the top of its handler for every route).
`tp-ahmed-agency-api` uses `AGENCIES_TABLE`, `PACKAGES_TABLE`, `ADMIN_GROUP` and `ALLOWED_ORIGINS`.

## Multi-city trips

A trip like Copenhagen 3 nights → Lofoten 4 → Abisko 4 uses the same tools plus one new one:

- `search_flights` with `returnFrom` gives an **open-jaw** ticket: fly SIN → CPH, return KRN → SIN.
- `search_stays` is called once per city with that city's dates. Stay IDs include the dates and guests
  (`…@2026-12-13_4n_2p`), so the same hotel searched for other dates gets its own ID and price.
- `search_transfers` (new) gives the options between two cities on the moving day: one-way flights from
  Duffel when both airports are known and the hop is at least 250 km, plus an **estimated** train / bus / ferry
  option (distance-based price and time, with a Rome2Rio link to check). Estimates are labelled in the plan and PDF.
- `verify_itinerary` and `render_pdf` accept `"stays": [{"stayId", "checkIn", "checkOut"}]` and
  `"transfers": [{"transferId", "date"}]` instead of a single `stayId`. The verifier checks the hotels form an
  unbroken chain from the first to the last night, there is one transfer per change of city on the right date,
  no sightseeing before a transfer arrives (+60 min), and no place more than 120 km from that night's hotel.

Single-city trips work exactly as before.

## Personal preferences (tool parameters)

The schemas tell the agent how to turn a personal request into parameters; the tools apply them and report back
which ones each result meets (`matches`). Filters that would leave nothing are relaxed and explained in `filterNote`.

| Tool | Preference parameters | What comes back |
| --- | --- | --- |
| `find_places` | `vibe` (classic / balanced / hidden_gems), `dietary`, `accessibility`, `audience` (family / adults), `indoorOnly`, `freeOnly`, `avoid`, neighbourhood in `city` | `tags` (local pick, well-known, wheelchair, vegetarian, halal, free entry, indoor, family…), `matches`, `description` |
| `search_stays` | `style` (ryokan, boutique, hostel, apartment, guesthouse, resort, cabin, capsule, hotel), `minStars`, `minReviewScore`, `sortBy` (price / rating / value), neighbourhood in `city` | `style`, `matches`, `filterNote` |
| `search_flights` | `maxStops`, `departAfter`, `departBefore`, `returnDepartAfter`, `returnDepartBefore`, `preferredAirlines`, `avoidAirlines`, `sortBy` (price / duration / best) | `maxStops`, `totalMinutes`, `matches`, `filterNote` |
| `search_transfers` | `prefer` (cheapest / fastest / ground / flight), `avoidOvernight` | `matches` |

New `find_places` categories: aquarium, theme_park, historic, nightlife, dessert, street_food, spa, bookshop, playground.

## Named places, named or booked hotels, day trips

| Tool | New input | Result |
| --- | --- | --- |
| `tp-find-places` | `names: ["teamLab Planets", ...]` (max 6) | Each found place first, with `requested` and tag `requested by user`, never filtered by preferences; `notFound` lists the rest. Only `names` = a quick lookup. |
| `tp-search-stays` | `name`, `alreadyBooked`, `bookedPriceSGD` | Search centred on the named hotel, which comes first with matches `requested hotel` (kept even over price/star filters). `alreadyBooked: true` returns one stay `booked:…` without searching (price = `bookedPriceSGD`, default 0). |
| `tp-sequence-day` | `start: {name, lat, lng}` (schema now lists it; `stayId` no longer required) | Start a day somewhere other than the hotel, e.g. the day-trip town. Category `requested` gets 90 min. |
| `tp-verify-itinerary` | `tripSpec.mustVisit`, `day.dayTrip {place, lat, lng, travelMinutes}`, `stays`/`transfers` (now in the schema) | New checks `must_visit` and `day_trip` (too far: over 450 km or 3.5 h each way; on an arrival/departure/moving day; first stop before you can arrive; back too late). On a day trip, places must be within 40 km of the town. |
| `tp-render-pdf` | `day.dayTrip`, stays with `booked` | Prints "Day trip to … (about N min each way)" and "Hotel (booked)". |

The fallback city list (used when geocoding is unavailable) now includes popular day-trip towns (Nikko, Kamakura,
Hakone, Nara, Kobe, …) in `tp-find-places`, `tp-search-stays` and `tp-search-transfers`.

## Extra IAM permission

The policy from runbook step 4.1 covers everything except one line. If you set
`ROUTE_MATRIX_FUNCTION` on `tp-sequence-day`, add this statement to `tp-lambda-tools-access`:

```json
{"Effect": "Allow", "Action": "lambda:InvokeFunction",
 "Resource": "arn:aws:lambda:ap-southeast-1:<account-id>:function:tp-route-matrix"}
```

Without it, sequencing still works using the distance estimate.

## Testing

Offline: `bash tests/offline/run_all.sh` runs every tool against fake AWS services. Through the real Gateway:
`python3 tests/gateway_smoke_test.py`.

### In the console — run in this order

`test-events/<name>.json` has a ready event for each function. Run them **in order**, because
the later tools read IDs that the search tools saved to the pool:

1. `tp-search-flights` → 2. `tp-search-stays` → 3. `tp-find-places` → 4. `tp-route-matrix`
→ 5. `tp-search-transfers` → 6. `tp-sequence-day` → 7. `tp-verify-itinerary` (expect `"passed": true`)
→ 8. `tp-render-pdf` (open the returned `url` within 15 minutes to see the PDF).

The sequence, verify and PDF events use mock IDs (`mock:stay_1@2026-12-10_5n_2p`,
`mock:35.68,139.77:temple_1`, …), so run the search tools with `MOCK_MODE=true` first. After switching to
live data, replace those IDs with real ones from the search results.

## Going live

Set `MOCK_MODE=false` per function. Fallbacks, all labelled in the `source` field:

- flights: **SerpApi Google Flights** (`google_flights`; real airlines, times and SGD prices for all travellers,
  each offer has a `bookingUrl` to Google Flights) → Duffel (`duffel`; test mode = fake "Duffel Airways") →
  error `not_configured` if the secret has neither `SERPAPI_KEY` nor `DUFFEL_TOKEN`. A round trip uses
  1 + `SERPAPI_RETURN_LOOKUPS` (default 3) SerpApi searches, plus one nonstop-only search above economy (one-way:
  1, or 2 above economy); results are cached 6 h (`google_flights-cache`).
  SerpApi's free plan is 250 searches/month.
- stays: liteAPI → Duffel Stays (default `STAYS_PROVIDERS=liteapi,duffel`) → mock (`mock-fallback`)
- places: Overpass (2 servers) → Amazon Location Places → Google Places → mock (`mock-fallback`); the whole call,
  the city geocode included, finishes within `TIME_BUDGET_SECONDS` (default 45) so it never hits the 60 s Lambda
  timeout.
  With `GOOGLE_MAPS_KEY` in the secret, restaurants, cafes and desserts come from Google Places Text Search first
  (rating 4.0+, 50+ reviews), and so do up to 4 sight categories (4.0+, 200+ reviews). A city sight call also makes
  one "top sights in <city>" Text Search first (same floor; `searchedAs: "top_sights"`, tag `top sight`), so it
  makes 1 + (Google-first sight categories, at most 4) + (food categories) requests; temples and shrines are searched
  as "temples in <city>" / "shrines in <city>" with `includedType` `buddhist_temple` / `shinto_shrine` (shrines with
  `strictTypeFiltering`). Google results are never cached, so cached calls ask Google again: one Tokyo + Kyoto plan
  makes about 40 Text Search requests, plus 1 per city sight call. Set a daily Places API (New) Text Search quota of
  about 2,000 (50 plans), a billing budget alert, and restrict the key to Places API (New). Past the quota, food falls
  back to the free chain without an error.
- route matrix: Amazon Location → distance estimate (`estimate`)
- transfers: one-way flights from Google Flights via SerpApi (`google_flights+estimate`, 1 SerpApi search per hop,
  cached 6 h) → Duffel (`duffel+estimate`) → ground estimate only (`estimate`). An estimate-only answer after a
  passing SerpApi or Duffel error (429/5xx, timeout, an unreadable reply) is not cached, so the next call searches
  again. The city geocodes (Amazon Location, us-east-1) count against the same time budget.

Every tool answers a malformed provider reply (an HTML page, a null list, a place without an id or a location, a
price such as `"$1,234"`) by going on to the next provider, and bad agent input (a date or pax it cannot read, a
non-numeric lat) with its usual error shape (`"error": "bad_input"`), never an exception. A single string where a list
is expected (categories, airlines, placeIds, caveats, mustVisit) is one item.

`tp-sequence-day`: a full-day park (Disney, Universal Studios, Fuji-Q) is open 09:00-21:00 when the pool has no hours
and its visit runs from arrival to closing (home by `dayEnd`); a first meal that cannot start by 14:30 is the dinner
and the answer has `"mealGaps": ["lunch"]`. `tp-verify-itinerary`: the longest-ride rule (`maxRideMinutes`) and the
other commute warnings apply to city days only; a day with `dayTrip` or with a full-day park stop gets none.

The liteAPI and Google field names follow their current docs. If a fallback returns no results,
check the CloudWatch log and compare the response with the provider docs.

## Known limits (worth stating in the report)

- **Ground transfers between cities** are estimates from distance (about 70 km/h, SGD 0.22/km + SGD 10 per
  person), not real timetables. Flights between cities are real Google Flights fares when `SERPAPI_KEY` is set.
- **Travel times:** walking or taxi only; public transit isn't modelled. Walks over 30 min become a taxi hop.
- **Opening hours:** read approximately from the first `HH:MM-HH:MM` in the OSM string.
- **Currency:** converted with a fixed, dated rate table (`FX_AS_OF`).
- **PDF text:** non-Latin names print correctly through the `tp-fonts` layer (DejaVu plus a Noto Sans CJK
  conversion; see `assets/fonts/`). Thai and Indic scripts are not covered yet.

## Tool schemas for AgentCore Gateway (runbook 6.1)

`schemas/<name>.json` is the inline tool schema for each Lambda target: a single JSON object
with `name`, `description` and `inputSchema`. Paste the whole file, starting with `{` and ending with `}`,
into **Tool schema → Define with in-line schema** for that target. Don't wrap it in `[ ]`.
Only these JSON Schema keywords are used: `type`, `description`, `properties`, `required`, `items`.
